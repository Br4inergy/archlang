# Prior art: helping LLMs write architecturally sound floor plans (for ArchLang)

Researched 2026-10-18. Every claim has a source URL. **[verified]** means I read it in the primary text (paper HTML/PDF or regulation). **[secondary]** means a search snippet or third-party summary. **[recall]** means a widely used value I could not confirm from a primary source in this session.

## 1. LLM and generative floor-plan work (2023–2026)

### 1.1 Direct coordinates fail, structure succeeds

| Work | Representation the model emits | What happened | Source |
|---|---|---|---|
| **Floor-plan RLVR** (Lara et al., Mila, May 2026) | JSON. Per-room `floor_polygon` in absolute metres, doors listed as spaces, input bubble graph | Few-shot GPT-4o, o3 and QwQ-32B **"none consistently produced valid floor-plan JSON"**. Failures: non-closed polygons, self-intersections, duplicated/missing rooms, connectivity violations, area drift, schema hallucination. Few-shot Llama-3.3-70B overlap was 0.55±0.50. SFT+RLVR cut overlap by 65% and compatibility error by 56%. Best-of-100 vs best-of-10 cut compatibility error by 86.7%. **A connectivity-only reward was reward-hacked: rooms shrank to tiny shapes to match adjacency.** | [verified] https://arxiv.org/html/2605.14117v1 |
| **HypergraphFormer** (Autodesk Research, May 2026) | A JSON BSP tree (interior subdivision) plus an access graph (door edges), fitted to any boundary. **Walls are implied by splits, doors are graph edges.** | Qwen3-4B LoRA reached 0% spill outside the boundary and 0% room overlap *by construction*. Strict access-graph accuracy was 40.9% vs 6.0% (HouseGAN++) and 16.3% (HouseDiffusion). Type/count accuracy 100%. Edits are "a few-token change". The authors argue that compact checkable topology lets an LLM match validity exactly, whereas it "can only approximate" validity in high-dimensional geometry. | [verified] https://arxiv.org/html/2605.18932v2 |
| **FML / FMLM** (Apr 2026) | HTML-like markup. Rooms are polygons. `<door><connect>i j</connect><vertex>…` is a segment on a **shared room edge**. No wall primitive. | Constrained decoding enforces "door has 2 vertices, interior door lies on an edge between two *different* rooms, room ≥4 vertices". Without it the model produced "overlapping rooms and misaligned doors" and GED rose from 1.21 to 1.64. Baselines: Graph2Plan lacks interior doors, and HouseGAN++/HouseDiffusion place doors off room boundaries. | [verified] https://arxiv.org/html/2604.04859 |
| **Co-Layout** (Nov 2025) | The LLM writes *constraints* (adjacency, target area, corner, privacy ordering by distance from entrance, reachability). A Gurobi integer program on a grid solves the geometry. | The paper states LLMs cannot produce precise coordinates. Two-stage baselines (Holodeck, AnyHome) showed **"passing through a bedroom to reach the living area"**, unreachable rooms and impractical shapes. Removing the accessibility constraint let furniture block entrances. **Doors/windows are placed by heuristics afterwards.** | [verified] https://arxiv.org/html/2511.12474v2 |
| **FloorplanQA** (ICML 2026) | JSON/XML layouts, read-only reasoning | Metric tasks 75–95%, constraint tasks 60–85%, **planning/path tasks 5–45%**. Common errors: summing areas instead of taking the union, centroid errors on complex polygons, and failure when several constraints must hold at once. **Swapping object labels cut repositioning accuracy from 60.5% to 40.0%, so models lean on names over geometry.** XML vs JSON changed accuracy by only ±3 points. Tools helped arithmetic but hurt path planning (flawed algorithms). | [verified] https://arxiv.org/html/2507.07644v3 , slides https://icml.cc/media/icml-2026/Slides/62946.pdf |
| **Text-to-Layout** (Duggempudi et al., 2025) | The LLM emits wall/door/window start–end coordinates and furniture centres in a 30×40 ft box | The prompt has to *say* "doors on walls… no overlaps", "windows on exterior walls only… at least 2 ft from any door edge", "furniture ≥1 ft clearance". A greedy post-pass nudges furniture to satisfy clearance and wall-adjacency (beds against walls). | [verified, PDF text] https://arxiv.org/pdf/2509.00543 |
| **Holodeck** (CVPR 2024) | GPT-4 emits *relational* constraints (edge/middle, near/far, in front of, face to, align). A DFS or MILP solver places objects. Collision and boundary checks are hard, relations are soft. | The authors' motivation is that direct numeric coordinates give overlapping, implausible layouts. This is a motivating claim, not an ablation. | [secondary] https://arxiv.org/html/2312.09067v2 , supp https://openaccess.thecvf.com/content/CVPR2024/supplemental/Yang_Holodeck_Language_Guided_CVPR_2024_supplemental.pdf |
| **Open-Universe scene synthesis** (2024) | The LLM writes a *declarative program* in a layout DSL. Running it yields a CSP that a gradient solver solves. | Beat trained models closed-universe and an LLM layout baseline open-universe. | [secondary] https://arxiv.org/abs/2403.09675 |
| **Architext** (Galanos et al., 2023) | Fine-tuned GPT-J emits a text layout | Validity above 99.5% but semantic correctness only 25–80% by prompt category. **Being syntactically valid is not the same as satisfying the brief.** | [secondary] https://arxiv.org/abs/2303.07519 |
| **Tell2Design** (ACL 2023) | 80k plans with language instructions. T5 seq2seq emits room boxes. | Text-to-image models do poorly. The task "is not well-solved". | [secondary] https://arxiv.org/abs/2311.15941 |
| House-GAN / House-GAN++ / Graph2Plan / HouseDiffusion | A bubble diagram (room-type nodes, door edges) is the input | They established the *graph-then-geometry* convention. A DPLAN related-work table notes that graph-conditioned generators often violate hard constraints unless checked explicitly. | https://arxiv.org/abs/2003.06988 , https://arxiv.org/abs/2103.02574 , [secondary] https://arxiv.org/pdf/2606.21159 |
| ChatHouseDiffusion (2024), HouseTune/Layout-LLM (2024), HouseMind (2026) | The LLM parses the prompt into a graph or draft, and diffusion makes the geometry | Two-stage is the norm. I found no head-to-head ablation against direct generation. | https://arxiv.org/abs/2410.11908 , https://arxiv.org/abs/2411.12279 , https://arxiv.org/pdf/2603.11640 |

The follow-up derives an **IDS (buildingSMART Information Delivery Specification) per prompt** plus LLM-written code checks, then feeds the results back. | Predefined checks miss task-specific requirements. The fix is a per-brief spec. | https://arxiv.org/abs/2408.08054 , https://ec-3.org/publication/ec32026_444/ |

### 1.2 Failure taxonomy across these papers (mapped to ArchLang)

1. **Closure/tiling:** overlaps, gaps, spill outside the boundary, non-closed polygons. ArchLang partly prevents these by construction.
2. **Graph mismatch:** missing or extra door edges, unreachable rooms, wrong room counts or types.
3. **Circulation semantics:** bedroom-through-bedroom, bathroom off the living room, entrances blocked by furniture (Co-Layout).
4. **Opening placement:** doors off a shared edge, doors and windows overlapping, windows on interior walls (FML, Text-to-Layout).
5. **Metric drift:** areas off target, plus reward hacking (rooms shrink to satisfy topology).
6. **Semantic shortcuts:** names believed over geometry (FloorplanQA label swap). This matches the "names contradicting position" symptom.
7. **Valid but wrong:** schema-valid output that misses the brief (Architext 99.5% valid, 25–80% correct).

**Takeaway:** every system that reaches near-zero geometric invalidity makes the invalid states *unrepresentable* (BSP, doors as edges between rooms, constrained decoding) or hands geometry to a solver. Doors and windows are the weakest point everywhere: they are placed last, heuristically, or not at all.

## 2. Automated rule and code checking

- **Solibri rule templates.** 202 *Space Validation* checks gaps or intersections between a space and its bounding walls beyond a tolerance, perimeter segments not touching any bounding component, minimum height, open top or bottom, spaces intersecting forbidden components, and **unallocated area (regions covered by no space or wall, meaning missing content)**. 226 *Free Area in Front of Components* checks a clearance volume in front of doors and windows. 208 *Accessible Door*, 222 *Component Distance* and 176 *Model Structure* are other templates. [verified] https://www.solibri.com/articles/using-the-space-validation-rule-to-ensure-model-accuracy ; https://help.solibri.com/hc/en-us/articles/4406907043351-226-Free-Area-in-Front-of-Components ; https://help.solibri.com/hc/en-us/articles/4415329086999-How-to-Check-Clearance-in-Front-of-Doors-and-Windows ; severity table https://society.solibri.com/assets/uploads/files/1647586669178-smc_severity_table.pdf
- **Solihin & Eastman (2015) rule classes**, by implementation complexity: (1) rules on explicit attributes, (2) rules on simple derived values, (3) rules needing an extended data structure of higher-level semantics such as graphs, (4) rules needing a "proof of solution", i.e. search. Autom. Constr. 53:69–82, doi 10.1016/j.autcon.2015.03.003. [secondary] https://witpress.com/Secure/elibrary/papers/BIM19/BIM19006FU1.pdf . Eastman et al. 2009 describe a four-stage process: interpret the rule, prepare the model, execute, report. [secondary] https://itcon.org/papers/2025_02-ITcon-Alnuzha.pdf
  - *ArchLang mapping:* the existing lint is mostly class 2–3. "Is there *any* door/bed position that works?" is class 4, which belongs in opt-in `suggest`/transforms, not in `compile`.
- **IFC.** Doors live in an `IfcOpeningElement` that voids a wall (`IfcRelVoidsElement`/`IfcRelFillsElement`), so an opening is *hosted by* a wall, never free-floating. Second-level space boundaries (`IfcRelSpaceBoundary2ndLevel`) pair the faces on both sides of each separating element. Exported boundaries are "often missing or incorrect" (Lilis 2016), and a validator by Ying & Lee uses 38 rules covering syntax/semantics, geometry and consistency. https://standards.buildingsmart.org/IFC/RELEASE/IFC4/ADD1/HTML/schema/ifcproductextension/lexical/ifcrelspaceboundary2ndlevel.htm ; https://pure.uos.ac.kr/en/publications/a-rule-based-system-to-automatically-validate-ifc-second-level-sp/ ; https://discovery-pp.ucl.ac.uk/id/eprint/1546334
- **buildingSMART IDS:** a machine-readable requirement spec that a model is checked against. It is the industry analogue of an intent/brief contract. (Cited by the EC3 2026 paper above.)
- **Singapore CORENET X:** BIM (IFC-SG) submission mandatory for new projects from April 2025. BCA's automated model checker targets "straightforward geometric and spatial requirements" and is used for **self-check before submission**. https://www1.bca.gov.sg/regulatory-info/building-control/corenet-x/more-information/technological-enablers ; https://www.ura.gov.sg/Corporate/Guidelines/Circulars/dc23-07
- **UpCodes Copilot:** LLM code Q&A with citations back to exact sections, plus project checklists. It reports "57% more accurate than generic AI", an unpublished vendor study. https://cms-v2.up.codes/features/copilot ; https://www.buildingenclosureonline.com/articles/94432-upcodes-unveils-copilot-intelligence
- **Space syntax:** the justified access graph is rooted at the entrance. Mean depth MD, relative asymmetry RA = 2(MD−1)/(K−2), integration = 1/RA. A deeper position gives more privacy. Typical residential reading: living spaces shallow and integrated, bedrooms and bathrooms deep. https://data.mendeley.com/datasets/rp9rpw2sp4/1 ; https://plugins.qgis.org/plugins/ssjgraph/ ; https://arkitekturforskning.net/na/article/download/778/722
  - *ArchLang mapping:* `describe()` already has the access graph. Depth from the entrance per room is a pure, cheap fact. It turns "privacy gradient violated" (bedroom shallower than living, or a bedroom on the only path to another room) into a measurable advisory.

## 3. Residential rules a checker could encode

### 3.1 China GB 50096-2011 住宅设计规范 [verified, full text extracted]
Source: https://www.gkd.edu.cn/jzgcxy/upload/files/2025/6/7d7db120306b11b3.pdf . Partly superseded by GB 55038-2025 住宅项目规范 (in force 2025-05-01), https://www.news.cn/house/20250401/5701ed566ec14e68af711d504c930882/c.html , so check before citing as current.
- 5.1.1 every dwelling has 卧室, 起居室, 厨房 and 卫生间 (bedroom, living room, kitchen and bathroom). 5.1.2 dwelling ≥30 m² usable, or ≥22 m² for the minimum type with a bed-sitting room.
- 5.2.1 double bedroom ≥9 m², single ≥5 m², bed-sitting room ≥12 m². 5.2.2 living room ≥10 m². 5.2.3 *minimise doors opening directly onto the living room*, and the living room should have a furnishable straight wall run >3 m. 5.2.4 a dining room or hall without direct daylight should not exceed 10 m².
- 5.3.1 kitchen ≥4.0 m² (≥3.5 m² in the minimum type). 5.3.2 kitchen near the entrance. 5.3.5 single-row kitchen clear width ≥1.50 m, double-row aisle ≥0.90 m.
- 5.4.1 three-fixture bathroom ≥2.50 m². 5.4.2 WC+basin ≥1.80, WC+shower ≥2.00, basin+shower ≥2.00, basin+washer ≥1.80, WC only ≥1.10 m².
- **5.4.3 a bathroom without an anteroom must not open directly onto the living room or kitchen.** 5.4.4 (mandatory) a bathroom must not sit directly over a lower unit's bedroom, living room, kitchen or dining room.
- 5.5.2 bedroom/living clear height ≥2.40 m (locally ≥2.10 over ≤1/3 of the area). 5.5.4 kitchen/bathroom ≥2.20 m. *(Heights draw nothing in ArchLang, so these are fact-only.)*
- **5.7.1 corridor clear width: entry corridor ≥1.20 m (should), corridor to bedroom/living ≥1.00 m, to kitchen/bathroom/store ≥0.90 m.**
- 5.8.1 window sill <0.90 m without a balcony needs a guard. 5.8.7 minimum door openings: entrance door widened to 1.00 m in this edition (verified, 条文说明 = the explanatory notes). The table itself is an image. **[recall]** values: 户门 (entrance) 1.00×2.00, 起居室 (living room) 0.90×2.00, 卧室 (bedroom) 0.90×2.00, 厨房 (kitchen) 0.80×2.00, 卫生间 (bathroom) 0.70×2.00, 阳台 (balcony) single leaf 0.70×2.00.
- **7.1.3 bedrooms, living room and kitchen must have direct daylight. 7.1.5 window-to-floor area ratio ≥1/7 for those rooms.** 7.1.1 at least one habitable room gets winter sun. 7.1.2 that window opening ≥0.60 m wide.

### 3.3 UK

Ceiling ≥2.3 m over ≥75% of GIA. Areas under 1.5 m headroom are excluded. Minimum GIA: 1b2p 50 m², 2b4p 70 m², 3b5p 86 m² (single storey). Halls ≥900 mm, local pinch ≥750 mm [secondary]. https://www.designingbuildings.co.uk/wiki/Door_clear_opening_width ; https://www.labc.co.uk/news/building-regulations-approved-document-part-m-in-a-nutshell ; https://democracy.merton.gov.uk/documents/s52865/Plans.pdf
- Fixture clearances (NKBA vs code): 30 in (760 mm) recommended and 21 in (533 mm) code minimum in front of the WC and basin; WC centreline ≥15 in (381 mm) code and 18 in (457 mm) NKBA to the side wall. https://www.supplyht.com/articles/92491-nkba-placement-of-bath-fixtures ; https://www.hunker.com/13725502/how-much-space-is-needed-for-a-toilet/
- **[recall]** Neufert / practice: bed access zone ≈600 mm (700 mm preferred) on the access sides; door hinge-side return ≥100 mm from a perpendicular wall so the frame fits. Neither was verified from a primary source this session.

### 3.4 Candidate rule set (topological rules are jurisdiction-neutral, numbers go in a profile)
- T1 bedroom or other habitable room not on the only path to another habitable room (AD B inner room; Co-Layout's illogical circulation).
- T2 bathroom door not opening directly onto living room or kitchen without an anteroom (GB 5.4.3).
- T3 every bedroom, living room and kitchen has ≥1 window on an exterior wall (GB 7.1.3, IRC R303/R310). Bathroom: window or declared exhaust.
- T4 window area / floor area ≥ profile ratio (1/7 GB, 8% IRC).
- T5 door and window openings lie on a wall shared by the two spaces they join. The span stays clear of wall junctions by ≥ nib (100 mm hinge side, 300 mm leading side under M4(2)). Openings never overlap each other. (FML door-on-shared-edge; Text-to-Layout "2 ft from any door edge".)
- T6 every room pair separated by a wall or an explicit opening/"open plan" declaration, with no unallocated slivers (Solibri unallocated space).
- T7 corridor clear width ≥ profile (GB 1.00/0.90 m, IRC 914 mm).
- T8 minimum area and minimum width per room kind (GB, NDSS, IRC).
- T9 kind↔content: a bedroom contains a bed (NDSS derives bedspaces from bedroom size), a bathroom contains a WC/shower, a kitchen contains a sink/hob.
- T10 privacy gradient: depth from the entrance, bedroom depth ≥ living depth (space syntax).

## 4. Language and tooling patterns for first-contact LLM authoring

1. **Make the common nonsense unrepresentable (topology-first, opening-by-relation).** FML forces a door to `connect` two room indices and to sit on their shared edge. HypergraphFormer turns doors into access-graph edges and walls into splits. IFC hosts every door in a wall. A `door between A and B [at t]` form, resolved to the shared wall by the compiler, removes "door across a junction", "door to nowhere" and "missing wall" in one move. https://arxiv.org/html/2604.04859 ; https://arxiv.org/html/2605.18932v2
2. **Room-centric partitions with derived walls.** Commercial editors keep walls and rooms as separate objects and *detect* the room from closed walls (Sweet Home 3D: room creation needs a fully closed wall loop, and gaps break it). They can also derive walls from a room ("double-click in it with the Wall tool"). The research representations (FML, BSP, RPLAN JSON) are room-centric, with walls implicit. IFC second-level space boundaries formalise the "both sides of each wall" pairing. https://www.sweethome3d.com/support/forum/printthread_thread,11494 ; https://www.sweethome3d.com/support/forum/printthread_thread,12575_printall,yes
3. **The LLM writes relations, the solver writes numbers. That is fine as an *opt-in* transform.** Holodeck (relational constraints with DFS/MILP), Open-Universe (declarative DSL to CSP), Co-Layout (LLM constraints to IP) and Infinigen Indoors (constraint DSL plus solver) all keep the LLM away from coordinates. ArchLang's policy allows this as an explicit transform (`arch layout`/`suggest`), not inside `compile`. https://arxiv.org/abs/2403.09675 ; https://arxiv.org/pdf/2406.11824
4. **External verifier in the loop beats self-critique, and specific critiques beat binary ones.** LLM-Modulo (2024): GPT-4o trip planning rose from 3.4% to 40.0% and calendar from 56.1% to 83.3% with 10 critic rounds. **Binary "try again" feedback was consistently worse than full critiques. Passing only the first critique was about as good as passing all of them.** https://arxiv.org/html/2411.14484v1 ; position paper https://arxiv.org/html/2403.04121v2 . Olausson et al. (ICLR 2024) found self-repair bottlenecked by feedback quality, with better feedback giving much larger gains. https://arxiv.org/abs/2306.09896 . FeedbackEval (2025) found structured feedback (tests > structured compiler output) beats unstructured. https://arxiv.org/html/2504.06939v1 . RustAssistant (ICSE 2025) reached about 74% on real compile errors by iterating LLM↔compiler diagnostics. https://dl.acm.org/doi/10.1109/ICSE55347.2025.00022 . Generative Compilation (2026): feedback on *partial* programs, close to the error source, reduces cascades. https://arxiv.org/abs/2607.13921 . CADCodeVerify (ICLR 2025): a VLM self-verification loop on CadQuery gave only a 5.5% compile-success gain, so visual self-check is weak. https://arxiv.org/abs/2410.05340
5. **Rewards and checks must be jointly complete, or the model games them.** The RLVR paper's connectivity-only reward produced tiny rooms. A lint set that checks adjacency without area/width checks invites the same hack from an agent loop. https://arxiv.org/html/2605.14117v1
6. **Names are trusted over geometry, so check them.** The FloorplanQA label-swap result is the empirical basis for a kind↔geometry↔content consistency lint (bedroom without bed, "north_bedroom" on the south, "hall" with area 30 m²). https://arxiv.org/html/2507.07644v3
7. **A per-brief requirement contract.** buildingSMART IDS, the EC3 2026 Text-to-BIM self-verification (an IDS plus code checks derived per prompt) and the RLVR input graph and areas all check against the *brief*, not just against generic rules. This matters because valid ≠ correct (Architext). https://ec-3.org/publication/ec32026_444/
8. **Teach the grammar small and scoped.** Grammar Prompting (NeurIPS 2023): a minimal per-example BNF subset helps DSL generation. **Prepending the full grammar did not help.** So first-contact docs should give a minimal, task-shaped subset plus a canonical example, not the whole spec. https://arxiv.org/abs/2305.19234
9. **Self-check before submission is how regulators do it.** CORENET X frames automated checking as consultant self-check of "straightforward geometric and spatial requirements". UpCodes cites the exact clause. A diagnostic carrying a rule source (e.g. `GB50096 §5.4.3`, `AD-B inner room`) gives the LLM a rationale it can act on. https://www1.bca.gov.sg/regulatory-info/building-control/corenet-x/more-information/technological-enablers
10. **Coarse checks fail open on complex geometry.** FloorplanQA errors cluster on complex polygons and overlap unions, and Solibri reports unallocated slivers as likely missing content. Computing union, clearance and depth facts in `describe()` saves the LLM from doing the arithmetic it gets wrong.

## Gaps and caveats
- I found no controlled study isolating *diagnostic phrasing* (wording, ordering, fix-it vs no fix-it) for LLM repair in a spatial DSL. The closest evidence is LLM-Modulo's binary-vs-full ablation and FeedbackEval.
- No head-to-head "LLM emits graph then solver" vs "LLM emits coordinates" ablation on the same floor-plan benchmark. The evidence is consistent across papers but indirect.
- The primary IRC text was not accessible (403). GB 50096 table 5.8.7 is an image. Neufert values are [recall].
