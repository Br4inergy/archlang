# 05 · 渲染、材质与视觉回归：无 GPU 下的性能与确定性

> 状态：已深挖（实测，单机）· 日期：2026-10-23 · [`00-deep-dive-ranking.md`](00-deep-dive-ranking.md) 的第 5 位 · 上游：主文档 [§4.6](../development-plan.md)（材质）、§6（渲染）、§6.6（预算）、§8.5 L3、Q21（已决定）
>
> 脚本：[`img_diff.py`](../spike/src/img_diff.py)（逐像素对比）、[`three_headless.html`](../spike/src/three_headless.html)（无头 three.js 渲染页）、[`render_glb.py`](../spike/src/render_glb.py)（Blender 渲染）。除标注外为 **[实测]**：Linux x86_64、8 核、16 GB、**无 GPU**；Blender 5.2.3；three.js 0.186.1 + Chrome 156 无头（`--use-angle=swiftshader --enable-unsafe-swiftshader`）；输入为 spike 的 `laneway-house` GLB（39 个绘制调用、820 个三角形）；同机、单次实验、**不是基准**。

## 1. 问题定义

渲染链有两条：three.js（查看器与 CI 回归）与 Blender（出图、视频）。要回答：

1. 无 GPU 的机器上，各自的耗时数量级是多少，是否满足 §6.6 的预算；
2. 输出**是否可复现**——这决定视觉回归能不能做"逐像素"；
3. 核心提供的材质信息能否映射到 PBR，缺什么；
4. 视觉回归应以哪条链为准。

## 2. 当前证据

### 2.1 Blender（Cycles CPU + 降噪，1000×800，iso 切开式视角）[实测]

| 配置 | 耗时 |
|---|---|
| 16 spp，8 线程 | 约 4.1–4.5 s |
| 16 spp，2 线程 | 约 11.8–12.1 s |
| 64 spp，8 线程 | 约 8.4–8.7 s |

- **像素确定性**：同一配置重复渲染、以及 2 线程 vs 8 线程，**逐像素完全相同**（最大差 0、平均差 0）。但 **PNG 文件字节会不同**（SHA-256 不同）——所以回归比较必须比**像素**哈希，不能比文件哈希 [实测：`img_diff.py`]。
- 16 spp vs 64 spp：最大差 17/255、平均差 0.073、PSNR 57.9 dB——对"几何是否出错"的检测，16 spp 足够。
- **没有测**：跨机器、跨 CPU 型号、跨 Blender 小版本的确定性（CPU 的 SIMD 路径可能不同）[待核实]。

### 2.2 three.js 无头（SwiftShader 软件 GL）[实测]

- 单帧渲染约 42 ms；含 Chrome 启动的整条命令约 0.78 s；两次运行的 PNG **字节相同**（17398 字节，SHA-256 相同）。
- 没有阴影与全局光照：外观是"平的"，适合检查**几何缺失/错位/朝向**，不适合评价美观。
- **没有测**：跨机器、跨 Chrome 版本、跨操作系统（SwiftShader 随 Chrome 版本变化）[待核实]。

### 2.3 材质：核心给了什么 [读码]

- 墙的 `material` 是**填充图案名**：`KNOWN_MATERIALS = poche, concrete, brick, insulation, tile, none`（默认 `poche`；`none` 的含义是不画填充，未核对其 3D 语义）。
- 室外面的地面材质 `GROUND_MATERIALS = grass, planting, paving, deck, gravel, water, tarmac`（由 `outdoor <kind>` 决定，作者不直接拼写）。
- 主题（`THEMES`，如 `blueprint`）是**绘图配色**（背景、描边、填充、标注色），并不描述建筑材料——`blueprint` 主题的墙不应在 3D 里变蓝。所以 3D 的 PBR 预设**不能**从主题推导；它是一张以上 13 个名字为键的独立表（颜色/粗糙度为设计值，不是标准；`--palette` 覆盖）。
- 核心**没有**地板饰面、天花、门窗框材质的数据；这些由 3D 的映射规则（§4.6，房间用途 → 地板预设）补上并写进账本。

## 3. 方案比较（视觉回归以谁为准）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **G1（推荐）** | 分层：① 主判据 = Scene3D/GLB 的 SHA-256（V-DET-01）；② 视觉回归 = three.js 无头渲染，**同一钉死的 Chrome 版本**下逐像素，跨环境用 PSNR 阈值；③ Blender 只用于出图/视频，不进 CI 阻断 | 快（< 1 s）、已测到两次逐字节一致；几何类回归在 ① 就拦住 | 外观平，不能评价 Blender 出图 |
| G2 | Blender 像素哈希作 CI 门 | 外观最接近成品 | 4–12 s/帧；Blender 小版本或 CPU 变化可能破坏像素一致（未测）；安装重 |
| G3 | 只比结构（GLB），不比图像 | 最稳 | 抓不到"渲染链本身"的回归（相机、灯光、材质映射）|

## 4. 推荐与理由

**G1**，并在 §6.6 里把"每帧耗时"按 §2.1/§2.2 的实测数量级更新。理由：确定性证据只覆盖了"同机重复"，不足以让 Blender 像素哈希作阻断门；three.js 链便宜且已被证明可逐字节重复，足以做第一道防线。**Q21 已由所有者于 2026-10-24 决定采纳 G1**（非阻塞；钉死的 Chrome 版本与基线最晚 M2 结束前建立，跨机器实验在 M3）。

## 5. 风险与未验证项

- 跨机器确定性**未测**：这是"可复现"这一核心卖点的最大缺口。建议 M0/M3 在两台不同 CPU 的机器（或 CI 与本机）上各渲一次对比，再决定阈值。
- 帧耗时只在一台 8 核机器、一个小模型上测过；大平面（如 `library`）与 1080p 视频帧未测。
- 软件 GL 的结果可能随 Chrome 版本变化（SwiftShader 内置于 Chrome）；需要把 Chrome 版本写进 `doctor` 输出与回归基线的元数据。
- 材质映射表是设计值；没有做真实感评审（"看起来对不对"是主观的，未评估）。
