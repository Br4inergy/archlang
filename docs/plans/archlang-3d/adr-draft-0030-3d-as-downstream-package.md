# 30. 3D is a downstream package: `archlang-3d` consumes resolved data, the core never draws the building

## Context

ArchLang draws floor plans. [ADR 0021](../../adr/0021-plan-first-view-deprecated.md) deprecated the axonometric view for four reasons: it supports none of the checked claims, it had no consumer, it contradicts the positioning, and it carries a maintenance surface. It named the real forward path: "the third dimension … is data, not drawing: an IFC export of the height datum (backlog P3-2)", and noted that "a reader who wants a picture of the building has to use a tool that consumes the export."

Two things have changed since:

1. **A consumer exists.** The ArchLang promo film needed a 3D house. It was built by hand: opening positions and furniture footprints were copied from the compiled plan into a Blender script, and heights were typed in. Any plan edit means re-copying. The data the script copies is already resolved by the compiler.
2. **The data is richer than Plan JSON.** A feasibility spike (see the plan, §2.4) built GLBs from the public Plan JSON for all 34 `examples/` (39 per-storey files; 37 built, all watertight, glTF-Validator 0 errors / 0 warnings, byte-identical across runs) and compared them with the core's own joinery output. Findings that drive this decision:
   - Plan JSON is **lossy for 3D**. Of the 32 examples that compile without an import `World`, **13 (41 %)** need information Plan JSON does not carry: arc walls are silently flattened to chords, `walls from rooms` walls are absent from `walls[]` (two examples build zero walls), multi-storey plans have no level number or elevation, and stairs, elevators, escalators, voids, roof outlines, outdoor surfaces and fences are missing.
   - The same information **is** available from the public library API (`resolveAll` → `PlanResolution`): `RWall.arcs`, resolved `height`, `ResolvedPlan.elevation/storeyHeight`, `RStair`, `RRoof.ring`, `RVoid`, `ROutdoor`, `RFence`, derived walls.
   - Against the core's own `joinWallSet` output, a downstream re-implementation of wall bands matched at IoU ≥ 0.99 on 29 of 35 comparable plans (median 1.0), and every clear deviation was on an arc-wall plan (worst 0.46). A second joinery downstream is therefore both feasible and exactly the divergence ADR 0018 exists to prevent. ADR 0021's Phase B removal checklist already says "Keep `joinWallSet` (the plan path uses it)", so exporting it does not conflict with the view's removal.
   - What 3D needs and a plan lacks — slab thickness, roof pitch, furniture height and model, materials, door-leaf pose — are **defaults, not facts**. The backlog already records that slab thickness does not exist and that `roof` refuses to approximate a pitch.

## Decision

1. **`archlang-3d` is a separate, downstream package.** The core does not depend on it, does not import it, and does not promote it on its landing page: the owner decided on 2026-10-23 that nothing is promoted before the 3D release milestone (plan Q5); wording after that is decided then. ArchLang remains "a plan language"; 3D is a tool that consumes the export, which is the sentence ADR 0021 left open.
2. **It consumes already-resolved data through public surfaces.** Primary input: the library API (`resolvePlan(source, { world })`, the core's internal parse-link-resolve path, with a `World` for imports; the `compile().ast` then `resolveAll` route silently drops imported content because that AST is not linked — measured on `main@98a4156`, plan §2.1). Secondary input: Plan JSON, accepted only for the subset it represents faithfully (straight walls, one storey, no derived walls) and **refused explicitly otherwise** — never silently approximated. This was confirmed by the owner (plan Q3); the lossless `-f building` JSON stays deferred. The core adds **purely additive exports** (accepted by the owner on 2026-10-23, plan Q10) so the package need not deep-import `src/*`: `joinWallSet` with the types its signature reaches (`JoinableWall`, `JoinedWallSet`, `JoinedCut`, `JoineryResult`, `JoinerySplit`, `EdgeLoop`, `Edge`, `Opening`; the exact list is derived by the compiler, as `test/public-surface.test.ts` already does for `SceneSummary`; the plan's §2.7 has the closure derived on `98a4156`), `resolvePlan` with `AnalyzeOptions` (plan Q18, decided by the owner on 2026-10-24; the stability level of `resolvePlan` and the meaning of its `levels` are still to be verified), `loopsToPolygons`, `doorSwing` with the door types its signature reaches (the owner's addition under Q11: the 3D side uses the leaf side the core resolved, and never infers inward or outward itself); and the missing resolved-element type names (`ROpening`, `RStair`, `RElevator`, `REscalator`, `RRoof`, `RVoid`, `ROutdoor`, `RFence`, `Arc`). `makeNodeWorld` is not exported: the package writes its own `World`. Each is a re-export, enters no `compile()` path, changes no cache key and no existing output byte.
3. **One footprint authority.** Wall footprints come from the core's own joinery (ADR 0018). The package does not implement a second wall joinery. A Plan-JSON-only fallback may exist for non-TypeScript consumers but is not the reference.
4. **`Scene3D` is the single geometric truth downstream.** glTF/GLB, IFC, the three.js viewer and external renderers are backends of one plan-aligned scene (integer micrometres; plan axes with y down; height z up; handedness resolved only by exporters). **IFC export (backlog P3-2) is a backend of `Scene3D` in this package, not a core feature**, so the GLB and the IFC cannot disagree. Backlog P3-2 is re-scoped accordingly when the work starts, and C1's exported fields are chosen with P3-2 in mind. The IFC writer is chosen by a criterion fixed in advance (plan Q4): try `@ifc-lite/create` first, adopt it only if IfcOpenShell reads its output back clean and it accepts deterministic GlobalIds, else write a minimal STEP writer. Plan Q17 (2026-10-24) added a third condition: the read-back wall volume must agree with the ownership prisms within 1 % in total, arcs and openings included, because a library that reads back clean can still lose the openings of curved walls. The spike is still to be run; this is not yet the final choice.
5. **No invisible architect (ADR 0005 applies to 3D).** Every quantity that is not authored or derived from the plan — slab thickness, roof form and pitch, door-leaf pose, window frame sizes, furniture heights and models, materials — is a **labelled default or an explicit parameter**, recorded in an `assumptions[]` ledger with `provenance ∈ {authored, derived, default, user-param}` and surfaced in every output (`--json`, GLB `asset.extras`, IFC property set). Defaults are the conservative ones: a 200 mm slab below the floor level (owner decision, plan Q6), a flat roof along the authored eaves outline (owner decision, plan Q7), closed doors, no ceilings, grey-box for unknown furniture. A pitched roof exists only when asked for with `--roof`, uses a 30° pitch if none is given, and carries "illustrative pitch, not an architectural decision". The first release of pitched roofs (M3) covers shed, gable and hip forms on rectangular or convex outlines; concave outlines wait for a straight-skeleton library (plan Q8; evaluated in v0.4: a pure-TypeScript candidate with guards exists, and the WASM one is excluded because it wraps GPL CGAL). Where the plan forces a case the 3D side cannot improve, it builds and **warns** instead of refusing or silently correcting: wall heights that differ at a joint (`W3D_MIXED_HEIGHT_JOINT`, plan Q19) and a stair outside the illustrative proportion limits (`W3D_STAIR_PROPORTION`, plan Q22).
6. **Sun is visualisation only and lives downstream.** The core has no sun model, latitude or date, and keeps none. The package may place a sun for the viewer and renders **only from user-supplied latitude, longitude, date and time**, composed with the plan's `north`; every such output carries a fixed "illustrative, not a daylight analysis" label. It reports no daylight metric.
7. **The 3D model is checked against the plan.** Each element carries a `source` pointing back to its plan element, and the build runs consistency checks before it emits a model: floor area vs. the plan, wall footprint vs. the core's joinery, ray probes through every opening, furniture inside its room, glTF-Validator, and a determinism hash. A 3D that cannot be checked against its plan is exactly what ADR 0021 deprecated; this package is not allowed to be that.
8. **Determinism is part of the contract.** For identical `(plan, archlang version, archlang-3d version, asset pack version, parameters)` the GLB is byte-identical (integer-micrometre geometry, stable ordering, no clock, no randomness). Rendered images are **not** promised byte-identical (software GL and Cycles sampling vary); their parameters are recorded so they can be reproduced. Visual regression in CI uses headless three.js on a pinned Chrome version; Blender renders are compared by decoded pixels within one environment and never block CI (plan Q21).
9. **External renderers stay external.** Blender (GPL) is invoked as a separate process through GLB; nothing GPL enters the dependency graph or the published artefacts. IFC validation with IfcOpenShell (LGPL) is test-time and out-of-process. Dependency licences are checked in CI — by reading the code a package wraps or ports, not only its npm `license` field (plan Q20: `straight-skeleton@3` is labelled MIT but wraps GPL CGAL); assets are limited to a whitelist (CC0 and project-authored by default; CC BY only in an optional pack with generated credits; the owner confirmed this direction under plan Q9 and the details are re-checked before M2). The package is MIT and the assets package CC0-1.0, registered per asset (plan Q13).
10. **Packaging (incubation).** The package starts as `packages/archlang-3d` in this monorepo, `private: true`, with isolation rules: the core never imports it; its heavy tests (Blender, Playwright, visual regression) run in a separate script and CI job outside `npm run check` and `prepublishOnly`; binary assets live in a separate assets package; first publication uses the existing tokenless OIDC procedure. Extraction into its own repository is evaluated at the release milestone against stated triggers (plan Q1). The owner chose incubation on 2026-10-23; a separate repository from day one was the considered alternative. The core's `packages/*` is both an npm workspace and part of the vitest include list, so "heavy tests stay out" is enforced by directory and file-suffix conventions, decided as plan Q16 (option A): light tests in `test/` run in the core's `npm test`; heavy tests in `e2e/` with a non-`.test.ts` suffix and their own vitest config, run by `check:3d`; `engines.node >=20`. How `check:test-wiring` treats the non-`.test.ts` files is read from the script but not yet measured; it is measured in the first PR.
11. **Interface conventions follow ADR 0015.** `archlang3d` has `--json` on every command (structured result on stdout, messages on stderr), exit codes 0/1/2/3 with the core's meaning, a machine-readable manifest of the same shape as the core's, and its own diagnostic namespace (`E3D_*`, `W3D_*`) that does not touch the core's error catalogue.

**Non-goals (recorded so they are not re-proposed):** reviving `--view` or adding any 3D to `compile()`; a BIM authoring tool or write-back to `.arch`; raster floor-plan recognition; generative (text/image → mesh) 3D in the default path; photorealistic asset libraries as a goal; sun, daylight or energy analysis in the core.

## Consequences

- **Positive.** The promo workflow becomes a command. 3D, IFC and renders share one checked scene. The core's positioning, byte-identity laws and zero-dependency stance are untouched. The consumer ADR 0021 asked for exists and is exercised on the whole `examples/` corpus.
- **Cost on the core (small, additive).** A handful of re-exports (and one export-surface contract test) become public API, so later refactors of `wall-lowering.ts` and `ir.ts` must keep them stable or version them (the core has no `@experimental` convention today, so ADR 0031 declares their stability level and the exports carry a JSDoc note). The owner accepted these exports on 2026-10-23, and the additions `resolvePlan`, `AnalyzeOptions` and `JoinerySplit` on 2026-10-24; until the core PR lands, a prototype branch may deep-import, recorded as technical debt.
- **Cost on the project.** A new package with its own CI, an assets pipeline and a licence process. Heavy tests must stay out of the core's release gate (`prepublishOnly` runs the whole suite and must not be narrowed to accommodate this).
- **Risk: version skew.** The spike found the published npm release (1.43.1) cannot parse three examples that `main` can (`walls from rooms`, `facing`). The package pins the core range and its CI runs against both the latest release and `main`.
- **Risk: defaults read as decisions.** Mitigated by the ledger, the output labels, `--strict`, and the skill's explicit prohibition on presenting a default as an architectural choice.
- **Backlog.** P3-2 gains a note when work starts: the datum's prerequisite is done; the slab-thickness gap is closed downstream by a labelled default; IFC lives in `archlang-3d`. No other backlog item changes.
- **Documentation.** `docs/language-reference.md` and the overview stay as they are. The package gets its own README and a short "what it is not" statement. The landing-page wording is an owner decision after the release milestone.

## Alternatives considered

- **3D inside the core (revive the axonometric view or add a new 3D backend).** Rejected: contradicts ADR 0021 on all four counts and puts a second, unverifiable drawing path into the byte-identity surface.
- **IFC export in the core as the only 3D path (backlog P3-2 as written).** Rejected as the *only* path: it serves BIM tools but not the viewer, renders or the promo workflow, and building geometry twice (GLB and IFC separately) invites disagreement. As a backend of `Scene3D` it is still delivered.
- **Plan JSON as the only input.** Rejected on the spike's evidence (41 % of compilable examples need information it does not carry; arcs flatten silently). Kept as a secondary, explicitly limited input; a lossless `-f building` JSON is deferred until a non-TypeScript consumer needs it.
- **A second wall joinery downstream.** Rejected (feasible, but it re-creates the drawing-vs-extrusion divergence that `joinWallSet`'s own documentation warns about).
- **Blender as the modelling engine (scripts or MCP).** Rejected for the pipeline: GPL, not byte-deterministic, heavyweight, and an MCP server hands the Blender process to a model. Blender stays a renderer behind GLB.
- **Image-based plan recognition (the approach of commercial plan-to-3D products).** Rejected: lossy reverse engineering of something we have as source.

## Reversal conditions

- **Superseded or narrowed if** the exports are rejected in review of the core PR (the owner has accepted them in principle, 2026-10-23): then Decision 2 reduces to deep imports behind a thin shim, and Decision 3 may be replaced by a Plan-JSON-plus-clipping fallback with the accuracy loss the spike measured.
- **Re-open Decision 3** if the per-wall ownership mechanism (hypothesis H1) stops holding. v0.4 verified it on 45 plans through `joinWallSet`'s `split` (`faceOf = wall id`), so this condition is currently not met.
- **Re-open Decision 10** if the package's dependencies slow the core's `npm ci` noticeably, if the asset pack exceeds roughly 50 MB, or if 3D grows its own release cadence or contributors.
- **Withdraw the package** if, by the third milestone (roof/materials/Blender/video), the corpus-level consistency checks cannot be made to pass without guessing — that would mean the plan data is insufficient for 3D, and ADR 0021's "no consumer, nothing checkable" argument applies again.
